# pier — Documentation Infrastructure Design

**Status:** Approved (design phase)
**Date:** 2026-07-07
**Branch:** `docs/initial-documentation` (off `develop`)

## Summary

This document designs the initial documentation infrastructure for `pier` and
the code-independent content that ships on the `docs/initial-documentation`
branch. The goal is to establish the documentation *skeleton* — its layout,
community-health files, and generation conventions — so that each branch in the
current feature stack can later drop its real content into the right place.

The command-line documentation aims for the standards expected of a public OSS
CLI: a clear docs map, community-health files, a security policy, issue/PR
templates, and a documented convention for generating the command reference,
man pages, and shell completions from the cobra command tree.

## Context: the branch stack

`pier` is developed as a stacked chain of branches:

```
develop → feat/cli-implementation → feat/config-discover → feat/agent-consumable-cli
```

`develop` (equal to `main`) contains only repository scaffolding (Makefile,
Jenkins/GoReleaser CI, linters, `.editorconfig`), the `README`, `LICENSE`,
`CONTRIBUTING`, and the design/plan specs. **No cobra command code lives on
`develop`** — `main.go` and `cmd/` first appear on `feat/cli-implementation`.

This has two consequences that shape the design:

1. **Autogeneration cannot run here.** `cobra.GenMarkdownTree` / `GenManTree`
   need the command tree, which is absent on `develop`. Generation is documented
   as a convention now; the tooling (Makefile targets) lands on the branch that
   has the commands.
2. **Only develop-resident content is written in full.** Guides that describe
   runtime behavior of unimplemented commands are shipped as *skeletons* — the
   base structure that the feature branches fill in.

Propagation of this infrastructure to the stacked branches (rebase vs. merge) is
**explicitly out of scope** for this branch and will be decided in a later
session.

## Documentation layout

Approach: a flat, topic-oriented `docs/` folder rendered natively on GitHub — no
static-site generator, no new build step, matching the repo's Node-free,
low-maintenance posture. Page names are informed by the Diátaxis taxonomy
(how-to / reference / explanation) without imposing its full folder structure.

### Content written in full now

These have their subject on `develop` or are pure repository infrastructure.

| Path | Content |
|---|---|
| `docs/README.md` | Documentation index/map; links every page; summarizes the generation convention |
| `docs/installation.md` | Install via `go install` and prebuilt binaries — backed by `.goreleaser.yaml`, which is present on `develop` |
| `SECURITY.md` | Vulnerability-reporting policy; note that `pier secret get --decode` prints secrets in cleartext |
| `CODE_OF_CONDUCT.md` | Contributor Covenant |
| `.github/ISSUE_TEMPLATE/bug_report.md` | Bug report template |
| `.github/ISSUE_TEMPLATE/feature_request.md` | Feature request template |
| `.github/ISSUE_TEMPLATE/config.yml` | Issue-template chooser config |
| `.github/PULL_REQUEST_TEMPLATE.md` | PR template |
| `CONTRIBUTING.md` (exists) | Add a **Documentation** section: how to author docs + the generation convention |
| `README.md` (exists) | Add a **Documentation** section linking to `docs/` |

### Skeletons (the base for the stack)

Each ships with a purpose statement, section headings, and a
"populated on `<branch>`" note. No fabricated command behavior.

| Path | Populated on |
|---|---|
| `docs/usage.md` | `feat/cli-implementation` (base commands) + `feat/config-discover` (`discover`) |
| `docs/configuration.md` | `feat/cli-implementation` (config loading + resolution) + `feat/config-discover` |
| `docs/architecture.md` | `feat/cli-implementation`; links the design spec and `docs/adr/` |
| `docs/commands/README.md` | `feat/cli-implementation` (autogenerated per-command reference) |
| `docs/agents.md` | `feat/agent-consumable-cli` (JSON/`discover` modes, parseable output) |

## Generation convention (documented now, tooling later)

Documented in `CONTRIBUTING.md` and `docs/commands/README.md`:

- **Command reference:** `cobra.GenMarkdownTree` → `docs/commands/`.
- **Man pages:** `github.com/spf13/cobra/doc.GenManTree`.
- **Shell completions:** cobra's built-in `completion` command
  (bash / zsh / fish / powershell).

The Makefile targets (`make docs`, `make man`) are **not** added on this branch:
they would shell out to a `pier`/generator binary that does not exist on
`develop`, leaving a broken `make docs`. They land on `feat/cli-implementation`
alongside the command tree.

## Verification

- **Node-free, no new toolchain.** A Markdown linter (markdownlint) is a Node
  tool and is rejected to preserve the repository's Node-free guarantee stated
  in the main design spec.
- Verification is manual review plus GitHub Markdown rendering.
- A link checker (e.g. a Go/Rust tool that does not add Node) may be added in a
  later iteration; it is not installed here.

## Out of scope

- Propagating this infrastructure to the stacked branches (rebase/merge/cherry-pick).
- Any code-coupled content (real command reference, man pages, completions).
- Makefile documentation targets.
- A static documentation site.
